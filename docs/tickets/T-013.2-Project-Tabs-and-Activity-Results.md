# T-013.2 – Projekt-Hauptreiter & Activity-Ergebnisse

## Ziel

Aktivitäten sind der Arbeitsvorgang.

Die Ergebnisse der Aktivitäten müssen anschließend dauerhaft und logisch im Projekt auffindbar sein.

Ein Bauleiter darf ein Angebot, Bilder, Aufmaßdaten, Dokumente oder Rechnungsinformationen nicht nur über eine alte Activity wiederfinden müssen.

Die Projektseite erhält deshalb dauerhafte Hauptreiter.

Aktivitäten füllen diese Projektbereiche automatisch.

---

# Grundprinzip

Activity = Vorgang

Projektbereich = dauerhaftes Ergebnis / aktueller Stand

Beispiel:

Angebotsaufnahme
→ Angebotsdaten
→ Bilder
→ Maße
→ offene Punkte

Diese Informationen bleiben anschließend in den entsprechenden Projektreitern sichtbar.

Keine doppelte Datenerfassung.

Keine unnötigen Datenkopien.

Bestehende Project-Core-Architektur verwenden.

---

# Hauptreiter im Projekt

Die Projektdetailseite erhält mindestens folgende Hauptreiter:

1. Übersicht
2. Angebot
3. Bilder
4. Aufmaß
5. Dokumente
6. Rechnungen
7. Verlauf

Die Navigation zwischen den Reitern soll direkt im oberen Projektbereich sichtbar sein.

Desktop und Mobile berücksichtigen.

---

# 1. Übersicht

Die bisherige Baustellenzentrale bleibt die Hauptübersicht.

Mindestens:

- Baustellenadresse
- Kunde
- Ansprechpartner
- Projektstatus
- aktueller Baustellenstand
- nächster Einsatz
- offene Arbeiten
- technische Projektdaten
- kaufmännischer Kurzstatus
- Baustellenablauf / aktuelle Activities

Keine bisher funktionierenden Bereiche entfernen.

---

# 2. Angebot

Dieser Reiter soll alle vorhandenen Angebotsinformationen des Projekts anzeigen.

Insbesondere Daten aus Activities vom Typ:

- Angebotsaufnahme
- Angebot

Anzeigen:

## Kunde / Anfrage

- Ansprechpartner
- Telefon
- E-Mail
- gewünschter Termin
- Anfrageinformationen

## Baustelle

- Adresse
- Beschreibung
- ausgewählte Leistungen
- Gerüstart
- Kundenwunsch

## Maße

- Länge
- Höhe
- Fläche
- Gebäudeseiten / Abschnitte

## Konstruktion / Aufwand

- Regelausführung
- Sonderkonstruktion
- Statik
- Kran
- Sondernutzung
- Parkplatzsperrung
- Sondermaterial
- besondere Logistik

## Offene Punkte

- fehlende Fotos
- fehlende Pläne
- fehlende Maße
- Vor-Ort-Termin notwendig
- sonstige offene Fragen

## Status

Vorbereiten für:

- Entwurf
- in Prüfung
- versendet
- angenommen
- abgelehnt

Noch keine automatische Kalkulation oder Angebots-PDF erforderlich.

---

# 3. Bilder

Zentrale Projektgalerie.

Alle projektbezogenen Bilder aus Activities und bestehenden Baustellenbesuchen zusammenführen.

Bilder dürfen nicht nur innerhalb einer einzelnen Activity auffindbar sein.

Darstellung mindestens:

- Vorschaubild
- Datum
- zugehörige Activity
- Activity-Typ
- optional Beschreibung / Notiz

Nach Möglichkeit nach Datum gruppieren.

Keine Bilder doppelt anzeigen.

Bestehende Bilddaten weiterverwenden.

---

# 4. Aufmaß

Zentrale Sicht auf alle Aufmaßinformationen des Projekts.

Daten können insbesondere entstehen aus:

- Angebotsaufnahme
- Aufmaß-Activity
- Kontrolle
- Umbau
- Abbau

Mindestens anzeigen / vorbereiten:

- Länge
- Höhe
- Fläche
- Abschnitte
- Mengen
- Fotos
- Notizen
- Aufmaßstatus
- Datum letztes Aufmaß
- nächstes erforderliches Aufmaß

Noch keine komplexe Abrechnungslogik.

---

# 5. Dokumente

Zentrale Dokumentenakte des Projekts.

Bereiche mindestens vorbereiten:

- Gefährdungsbeurteilung
- Montageanweisung
- Behinderungsanzeige
- Bautagebuch
- Prüfprotokolle
- Gerüstfreigabe
- Abnahme
- Übergabe
- Bedenkenanmeldung
- sonstige Dokumente

Dokumente können zukünftig durch Activities erzeugt oder aktualisiert werden.

Aktuell vorhandene Dokumente sollen sichtbar sein.

Falls ein Dokument fehlt, neutralen Leerzustand anzeigen.

Noch keine KI-Dokumentengenerierung implementieren.

---

# 6. Rechnungen

Kaufmännischer Projektbereich.

Mindestens anzeigen / vorbereiten:

- Angebotsstatus
- Abschlagsrechnungen
- Datum letzte Abschlagsrechnung
- Schlussrechnung
- offene Nachträge
- Mietbeginn
- Abmeldedatum
- aktuelle Mietmengen
- geplanter Abbau
- Rechnungsstatus

Noch keine externe Buchhaltung.

Noch keine vollständige Rechnungsberechnung.

---

# 7. Verlauf

Dieser Reiter wird langfristig die chronologische Projekt-Historie.

Bis zur vollständigen Timeline-Engine vorhandene Daten nutzen:

- Activities
- Baustellenbesuche
- Statusänderungen
- vorhandene Ereignisse

Neueste Ereignisse zuerst oder klar chronologisch.

Keine parallele zweite Prozesslogik bauen.

---

# Activity-Ergebnisse

Die Activity Engine bleibt der Arbeitsweg.

Ergebnisse müssen aber automatisch in den passenden Projektbereichen sichtbar werden.

Beispiele:

## Angebotsaufnahme

füllt:

- Angebot
- Bilder
- Aufmaß
- Verlauf

## Aufmaß

füllt:

- Aufmaß
- Bilder
- Verlauf

## Kontrolle

füllt:

- Bilder
- Dokumente / Prüfinformationen
- Verlauf

## Montage

füllt zukünftig:

- Übersicht
- Bilder
- Dokumente
- Verlauf

## Behinderung / Nachtrag

füllt zukünftig:

- Übersicht
- Dokumente
- Rechnungen
- Verlauf

Nicht für jeden Activity-Typ eine eigene parallele Speicherung bauen.

Bestehende Daten referenzieren oder sauber projektbezogen ableiten.

---

# UX

Projektkopf bleibt beim Wechsel zwischen Reitern sichtbar bzw. leicht erreichbar.

Adresse und Projektname sollen jederzeit klar erkennbar sein.

Reiter müssen einfach verständlich sein.

Keine technische Sprache wie:

- Activity Store
- Entities
- Readiness Model

Nutzerbegriffe aus dem Domain Language Dictionary verwenden.

---

# Mobile

Auf kleinen Displays dürfen die Reiter horizontal scrollbar oder in eine kompakte Navigation überführt werden.

Der Nutzer darf nicht durch lange Seiten scrollen müssen, um zum gewünschten Projektbereich zu gelangen.

---

# Rückwärtskompatibilität

Sehr wichtig:

- bestehende Projekte erhalten
- bestehende Activities erhalten
- bestehende Baustellenbesuche erhalten
- bestehende Bilder erhalten
- bestehende Notizen erhalten
- bestehende Project-Cockpit-Daten erhalten

Keine Daten löschen.

Keine unnötige Migration erzwingen.

---

# Nicht Bestandteil

- keine automatische Kalkulation
- keine Angebots-PDF
- keine Rechnungs-PDF
- keine KI
- keine Materialplanung
- keine Disposition
- keine automatische Dokumentenerstellung

---

# Validierung

Manuell prüfen:

1. Bestehendes Projekt öffnen
2. Alle neuen Hauptreiter erreichbar
3. Angebotsaufnahme anlegen
4. Angebotsdaten erscheinen anschließend unter "Angebot"
5. hochgeladene Bilder erscheinen unter "Bilder"
6. Maße erscheinen unter "Aufmaß"
7. Activity bleibt weiterhin im Baustellenablauf sichtbar
8. Browser neu laden
9. Daten bleiben erhalten
10. alte Baustellenbesuche funktionieren weiterhin
11. keine Bilder oder Activities doppelt angezeigt
12. Mobile Navigation prüfen

Technisch:

- npm run lint
- npm run build
- git diff --check

## Wichtig

Nicht committen.
Nicht pushen.

Nach Abschluss kurz auflisten:

- geänderte Dateien
- neue Dateien
- relevante Datenmodelländerungen
- mögliche offene Punkte
