# T-013.1 – Typabhängige Activity-Formulare

## Problem

Aktuell verwenden alle Activity-Typen dieselbe Eingabemaske.

Das ist fachlich falsch.

Eine Angebotsaufnahme benötigt andere Informationen als eine Montage, Kontrolle, ein Aufmaß oder ein Telefonat.

Die Activity Engine soll einen gemeinsamen Kern besitzen, aber je Activity-Typ eine eigene fachliche Eingabemaske.

---

## Grundregel

Jede Activity besitzt weiterhin gemeinsame Basisfelder:

- Typ
- Titel
- Status
- Priorität
- Vorbereitungsgrad
- geplantes Datum
- Beschreibung

Zusätzlich besitzt jeder Activity-Typ eigene fachliche Felder und Workflows.

Keine parallele Activity-Datenhaltung erzeugen.

---

## Angebotsaufnahme

Bei Activity-Typ "Angebotsaufnahme" zusätzlich ermöglichen:

### Kunde / Anfrage

- Ansprechpartner
- Telefonnummer
- E-Mail
- gewünschter Ausführungstermin
- Anfrageeingang
- Rückruf erforderlich

### Baustelle

- Adresse
- geplante Arbeiten / Gewerk
- gewünschte Gerüstarten
- mehrere Leistungen auswählbar
- Fotos
- Pläne
- PDFs
- Freitext / Kundenwunsch

### Maße

- Gerüstlänge
- Gerüsthöhe
- Gerüstfläche
- mehrere Gebäudeseiten / Abschnitte vorbereiten
- Maße dürfen zunächst unvollständig sein

### Konstruktion / Aufwand

- Regelausführung möglich?
- Sonderkonstruktion möglich / erforderlich?
- Statik voraussichtlich erforderlich?
- Kran erforderlich?
- Sondernutzung / Parkplatzsperrung erforderlich?
- besondere Transport- oder Laufwege
- Sondermaterial erforderlich?

### Offene Punkte

- welche Informationen fehlen?
- Vor-Ort-Termin erforderlich?
- Fotos fehlen?
- Pläne fehlen?
- Maße fehlen?
- Ansprechpartner klären?

### Medien

Mehrfach-Upload:

- Fotos
- Bilder
- PDFs
- Pläne

Vorschau anzeigen.

Bestehende Medienlogik wiederverwenden.

---

## Montage

Bei "Montage" zukünftig andere Felder verwenden, mindestens vorbereiten:

- geplante Arbeiten
- Startmaterial
- Baustellenzugang
- Parkplatz / Zufahrt
- Kolonne
- Montageanweisung
- Gefährdungsbeurteilung
- offene Voraussetzungen

Noch keine vollständige Kolonnen- oder Materiallogik implementieren.

---

## Aufmaß

Bei "Aufmaß":

- Aufmaßart
- Maße
- Mengen
- Fotos
- Skizzen
- Notizen

---

## Kontrolle

Bei "Kontrolle":

- Prüfpunkte
- Mängel
- Fotos
- Sicherheitsrelevanz
- Handlungsbedarf

---

## Telefonat / Besprechung

Schlanke Maske:

- Ansprechpartner
- Thema
- Ergebnis
- offene Aufgabe
- Wiedervorlage

---

## Technische Umsetzung

Activity-Typ bestimmt die fachliche Maske.

Beispiel konzeptionell:

Activity
+
typeSpecificData

oder eine andere saubere, typisierte Struktur.

Keine riesige untypisierte Sammelstruktur mit allen Feldern für alle Activity-Typen.

Bestehendes Activity-Grundmodell respektieren.

---

## Wichtig

Die Angebotsaufnahme ist der erste vollständig auszuarbeitende typabhängige Workflow.

Andere Typen zunächst strukturell vorbereiten, aber nicht unnötig aufblasen.

---

## Rückwärtskompatibilität

- bestehende Activities bleiben lesbar
- bestehende Baustellenbesuche bleiben funktionsfähig
- keine Daten verlieren
- bestehende Bilder / Notizen weiterverwenden

---

## Validierung

Angebotsaufnahme anlegen und prüfen:

- Fotos hochladbar
- mehrere Fotos möglich
- PDF / Plan möglich
- wichtige Angebotsdaten erfassbar
- offene Punkte speicherbar
- nach Browser-Neuladen alles erhalten
- Activity erscheint weiterhin im Baustellenablauf

npm run lint
npm run build
git diff --check

Nicht committen.
Nicht pushen.
Geänderte Dateien auflisten.
